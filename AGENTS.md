# Repository maintenance guide

## Architecture

This repository is a Dart workspace with three packages:

- `packages/flutter_lua_bridge`: the Lua 5.4 runtime, native asset hook, codecs,
  raw bindings, and the native bridge ABI.
- `packages/flutter_lua_bridge_codegen_annotation`: contract annotations only.
- `packages/flutter_lua_bridge_codegen`: Dart contract parser and Dart/Lua/Teal
  generators.

The runtime package must not depend on the code generator at runtime. Generated
Dart code imports the runtime package. Teal is a development-time source
language; Cyan compiles `example/lua/src/*.tl` into Lua under `build/`.

## Source ownership

- Edit contract files under `example/bridge/` or an application's equivalent.
- Edit Teal business logic under `example/lua/src/`.
- Do not hand-edit files with `Generated by flutter_lua_bridge` or `Do not edit`.
  Regenerate them with `tool/generate_example.sh` or the codegen executable.
- Treat `example/lua/build/` as compiler output. Run Cyan after changing Teal.
- Keep upstream Lua C sources under `packages/flutter_lua_bridge/lua_src/`
  byte-for-byte compatible with the pinned Lua release unless the change is
  explicitly about the engine.

## Generated safety levels

- `O1` is the default: generated Lua validates supported values, checks arity,
  bounds validation depth, and wraps method execution with `pcall`; Dart sees
  `LuaSuccess` or `LuaFailure`.
- `O2` keeps the result envelope and `pcall`, but omits generated Lua type
  validators.
- `O3` keeps the direct call path and propagates uncaught Lua failures as
  `LuaBridgeException`.

Any generator change must test all three levels. Include both a successful call
and an error path. Contract fingerprints must change when the generated
protocol changes.

## Required checks

Run the lightweight local gate before opening a pull request:

```sh
./tool/ci_light.sh
```

It covers analyzer, generator tests, generated artifact drift and a small
example unit test. The full release gate is:

```sh
./tool/ci.sh
```

It additionally covers Teal/Cyan, native bridge tests and Flutter integration
tests. The full gate runs from the release-only Ubuntu workflow.

For focused work, run the smallest relevant checks as well:

```sh
(cd packages/flutter_lua_bridge_codegen && dart test)
(cd packages/flutter_lua_bridge && dart test)
(cd example/lua && cyan build)
python3 packages/flutter_lua_bridge/tool/test_native.py
```

If native asset hooks fail locally because of stale `.dart_tool` state, repeat
the check in a clean checkout or CI runner and report the environment failure;
do not weaken runtime tests to bypass the hook.

## Pull requests and commits

- Keep runtime, codegen, example, documentation, and unrelated application
  changes in separate commits when possible.
- Do not stage with `git add .`; stage explicit paths and inspect the staged
  diff.
- Run `git diff --cached --check` before every commit.
- Generated artifacts must be updated in the same commit as the contract or
  generator change that produced them.
- Do not commit the ignored `playground/` directory.
