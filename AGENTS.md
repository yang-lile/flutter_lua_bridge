# Repository maintenance guide

## Architecture

This repository is a Dart workspace with three packages:

- `packages/flutter_lua_bridge`: the bundled Lua releases (5.3, 5.4, 5.5), the
  native asset hook, the `flb` C shim, its generated bindings, the `LuaRuntime`
  Dart API and the codecs.
- `packages/flutter_lua_bridge_codegen_annotation`: contract annotations only.
- `packages/flutter_lua_bridge_codegen`: the `build_runner` builders. They
  read a Dart contract and generate its Dart part file and Teal declarations,
  and compile Teal to Lua with the bundled `tl.lua`.

The runtime package must not depend on the code generator. The generator
depends on the runtime: Teal is compiled by `tl.lua` running on `LuaRuntime`
in the `teal_worker` process, because a build script has no native assets.
Generated Dart code imports the runtime package only. Teal is a
development-time source language; nothing in this repository uses LuaRocks,
Cyan or a system Lua.

There is no generator command line. Generation is `dart run build_runner
build`; `bin/init.dart` only scaffolds a package, `bin/run.dart` runs
hand-written Lua and Teal entries on `LuaRuntime` without generating
anything, and `bin/teal_worker.dart` is internal to the builders. Do not add
a separate generator CLI.

## Source ownership

- Edit contract files under `examples/flutter_lua_bridge_example/lib/bridge/`
  or an application's equivalent.
- Edit Teal and Lua business logic under
  `examples/flutter_lua_bridge_example/lua/src/`, and its Lua-side tests
  under `lua/test/` (run with `dart run flutter_lua_bridge_codegen:run`).
- `tlconfig.lua` belongs at the package root (and the repository root for the
  example): the Teal language server reads it only from the opened folder.
- Do not hand-edit files with `Generated by flutter_lua_bridge` or `Do not edit`,
  nor `*.g.dart`, `lua/types/` and `assets/lua/` of the example, nor
  `test/fixtures/*.g.dart` and `test/fixtures/lua/{types,out}/` of the
  generator. Regenerate them with `tool/generate_example.sh`.
- `packages/flutter_lua_bridge_codegen/lib/src/teal/tl.lua` is the unmodified
  upstream Teal release. Never patch it; replace it with a newer release as a
  whole and update the version in the package README.
- Keep the upstream Lua releases under
  `packages/flutter_lua_bridge/third_party/lua-<release>/` byte-for-byte
  identical to the official tarballs. Never patch them; version differences
  are handled in `native/flb.c`.
- `native/flb.h` is the stable shim interface and must not expose any Lua
  type. `native/flb.c` is the only file allowed to branch on
  `LUA_VERSION_NUM`. After changing the header, regenerate
  `lib/src/flb.g.dart` with `dart run tool/ffigen.dart`.
- Keep logic in the shim: Dart code calls the generated bindings and must not
  re-implement Lua semantics.
- `flb` is the only native API and `LuaRuntime` the only Dart entry point.
  Examples, generated code and other packages go through `LuaRuntime`; do not
  add a second binding layer or import `lib/src/flb.g.dart` outside
  `lib/src/runtime.dart`.

- `skills/flutter-lua-bridge/SKILL.md` teaches AI assistants to use the
  library. Update it together with any change to the contract rules,
  generated API names, commands or file layout.

## Generated safety levels

- `O1` is the default: generated Lua validates supported values, checks arity,
  bounds validation depth, and wraps method execution with `pcall`; Dart sees
  `LuaSuccess` or `LuaFailure`.
- `O2` keeps the result envelope and `pcall`, but omits generated Lua type
  validators.
- `O3` keeps the direct call path and propagates uncaught Lua failures as
  `LuaBridgeException`.

Any generator change must test all three levels. Include both a successful call
and an error path (`test/levels_test.dart`). The bridge does not version or
fingerprint contracts: keeping the shipped Lua in step with the Dart code is
the application's concern.

## Required checks

Run the lightweight local gate before opening a pull request:

```sh
./tool/ci_light.sh
```

It covers analyzer, the builders with generated artifact drift, generator
tests and a small example unit test. The full release gate is:

```sh
./tool/ci.sh
```

It additionally covers native bridge tests, every bundled Lua release and
Flutter integration tests. The full gate runs from the release-only Ubuntu workflow.

For focused work, run the smallest relevant checks as well:

```sh
(cd packages/flutter_lua_bridge_codegen && dart test)
(cd packages/flutter_lua_bridge_codegen && dart test -P teal-worker)   # Teal worker, own process
(cd packages/flutter_lua_bridge && dart test)
./tool/generate_example.sh --check                        # run the builders, fail on drift
python3 packages/flutter_lua_bridge/tool/test_native.py   # C tests, every bundled Lua
./tool/test_lua_versions.sh                               # runtime and generator tests, every bundled Lua
```

Any change to `native/`, `hook/` or `lib/src/hook/` must pass both multi-version commands, and
so must a change to the Teal builder or to `tl.lua`.

If native asset hooks fail locally because of stale `.dart_tool` state, repeat
the check in a clean checkout or CI runner and report the environment failure;
do not weaken runtime tests to bypass the hook.

## Pull requests and commits

- Keep runtime, codegen, example, documentation, and unrelated application
  changes in separate commits when possible.
- Do not stage with `git add .`; stage explicit paths and inspect the staged
  diff.
- Run `git diff --cached --check` before every commit.
- Generated artifacts must be updated in the same commit as the contract or
  generator change that produced them.
